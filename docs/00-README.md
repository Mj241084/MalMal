# مل‌مل (MAL MAL) — پوشه‌ی اسناد پروژه

فروشگاه آنلاین لوازم خانگی. استک: Django + SQLite + Redis + Tailwind v4 + DaisyUI 5 + HTMX.

این پوشه «منبع حقیقت» پروژه است. Claude Code قبل از هر کاری باید این اسناد را بخواند و فقط طبق آن‌ها کار کند.

## ۲. نشانه‌ها

| نشانه | معنی |
|-------|------|
| `[DECIDED]` | تصمیم نهایی. بدون پرسیدن از کاربر تغییر نمی‌کند. |
| `[ASSUMPTION]` | فرض معقول من. تا وقتی کاربر رد نکرده معتبر است. |
| `[OPEN]` | تصمیم گرفته نشده. Claude Code باید قبل از رسیدن به آن بخش بپرسد. |
| `[NEEDS-USER]` | نیاز به فایل/کلید/اطلاعات از کاربر (به `01-assets-needed.md` نگاه کن). |
| `[VERIFY]` | از حافظه نوشته شده. قبل از پیاده‌سازی باید با مستندات رسمی همان لحظه چک شود. |
| `[PLACEHOLDER]` | محتوای فرضی برای پر کردن صفحه. باید قبل از انتشار با محتوای واقعی عوض شود (بخش ۷). |
| `[RESOLVED]` | سوال باز که جواب گرفته. |

## ۳. راهنمای کار برای تو (کاربر)

### مرحله‌ی طراحی (همین گفتگو)
1. اسناد `02` و `03` را بخوان. هرچه غلط است یا نمی‌خواهی را بگو. من فایل را اصلاح می‌کنم و نسخه‌ی جدید را می‌فرستم و شماره‌ی نسخه بالا می‌رود.
2. بخش `[OPEN]` هر سند را جواب بده.
3. `04-design-system.md` را ببین: جهت طراحی (کهربایی روی رمپ گرم) و تم را تایید یا اصلاح کن.
4. `CLAUDE.md` و بریف فازها ساخته شده‌اند (`phases/`). فقط اگر چیزی در آن‌ها غلط بود بگو.

### مرحله‌ی ساخت (با Claude Code)
1. یک پوشه‌ی پروژه بساز و ساختارش این باشد:
```
malmal/
├── CLAUDE.md                  ← از همین بسته (ریشه‌ی پروژه)
├── docs/                      ← همین اسناد (به‌علاوه‌ی phases/). سند تقویم را با نام 06-jalali-calendar.md بگذار
│   └── vendors/               ← مستندات رسمی: smsir/، neshan/، tipax/، zarinpal/ (Claude Code هنگام نوشتن adapter با آن‌ها تطبیق می‌دهد)
├── skills/                    ← پوشه‌ی ۵ اسکیل: unslop، daisyui، color-palette، htmx-patterns، image-fetch (اختیاری، فقط توسعه)
├── static/                    ← خودت از قبل می‌سازی
│   ├── fonts/vazir/           ← فونت وزیر
│   ├── src/sprite.svg         ← sprite کامل lucide (منبع، سرو نمی‌شود)
│   └── logo.webp              ← لوگوی موقت
├── assets-incoming/           ← هر فایل دیگری که Claude Code ازت خواست، اینجا بگذار
└── .env                       ← کلیدها (هرگز commit نمی‌شود، Claude Code فقط .env.example می‌سازد)
```
2. پوشه‌های `static/` و `docs/` را خودت از قبل می‌سازی و پر می‌کنی (طبق درخت بالا). P0 ابتدا چک می‌کند و اگر چیزی کم بود می‌پرسد.
3. داخل پوشه `claude` را اجرا کن و بگو: «`CLAUDE.md` و `docs/phases/phase-00-skeleton.md` را بخوان و اجرا کن».
4. **هر فاز را در یک نشست جدید اجرا کن** (`/clear` یا نشست تازه). اسناد کافی‌اند و نشست کوتاه دقیق‌تر کار می‌کند.
5. آخر هر فاز، «Definition of Done» همان فاز را با هم چک کن، commit بزن، بعد برو فاز بعد.
6. اگر خواستی چیزی عوض شود، **اول سند را عوض کن** (یا بگو من عوض کنم)، بعد به Claude Code بگو. اگر فقط به Claude Code بگویی و سند عوض نشود، نشست بعدی تصمیم را فراموش می‌کند.

### وقتی Claude Code چیزی از تو می‌خواهد
طبق پروتکل بخش ۵ یک پیام با عنوان «⛔ نیاز به فایل/اطلاعات» می‌دهد که می‌گوید دقیقاً چه چیزی، کجا بگذار و تا نرسیده چه کار می‌کند. فایل را در `assets-incoming/` بگذار و بنویس «گذاشتم». خودش آن را به جای درست منتقل و پردازش می‌کند و وضعیت `01-assets-needed.md` را به‌روز می‌کند.

## ۴. قواعد برای Claude Code

1. اسناد را بخوان. چیزی که در اسناد نیست را حدس نزن. بپرس یا به‌عنوان `[ASSUMPTION]` ثبت کن و بگو.
2. تصمیم `[DECIDED]` را بدون تایید کاربر عوض نکن. اگر فکر می‌کنی غلط است، دلیلش را بگو و منتظر پاسخ بمان.
3. کلید، توکن و رمز را هرگز در کد یا سند نگذار و commit نکن. فقط از `.env` و `.env.example`.
4. وقتی تصمیم یا ساختار تغییر می‌کند، همان سند را به‌روز کن و یک خط در «تغییرات» بنویس.
5. اسکیل‌ها (`unslop`، `daisyui`، `color-palette`، `htmx-patterns`) را طبق دستورهایشان بخوان و اجرا کن؛ `image-fetch` فقط در صورت نیاز. اگر با اسناد این پروژه تناقض داشتند، **اسناد پروژه برنده است** و تناقض را به کاربر گزارش بده.
6. هر چیزی که از حافظه نوشته شده و `[VERIFY]` دارد (API پیامک، درگاه، نقشه) قبل از پیاده‌سازی با مستندات رسمی تطبیق داده شود.
7. هر فاز با تست‌های لازم و تیک‌خوردن Definition of Done تمام می‌شود، نه با «نوشتم».
8. قبل از نوشتن adapter پیامک، نقشه، پرداخت یا ارسال، مستندات همان سرویس را در `docs/vendors/` بخوان و موارد `[VERIFY]` را با آن تطبیق بده. اگر پوشه خالی بود، طبق پروتکل بخش ۵ بخواه. مستندات رسمی از سند پروژه معتبرتر است؛ تناقض را در همان سند اصلاح و به کاربر گزارش کن.
9. **هیچ وابستگی بیرونی کار را متوقف نمی‌کند** (مرچنت‌کد، قالب‌های پیامک، دامنه، اینماد، مشخصات فروشنده، سوال‌های ارسال): ساختار کامل ساخته می‌شود و مقدار از `.env` یا ادمین می‌آید. جدول رفتار در `CLAUDE.md` بخش ۲ و تصمیم D26.
10. پایتون فقط با `uv` و جاوااسکریپت فقط با `pnpm` (D27).

## ۵. پروتکل درخواست از کاربر

هر وقت به چیزی نیاز داشتی که فقط کاربر دارد (فایل، کلید، تصمیم)، از این قالب استفاده کن:

```
⛔ نیاز به فایل/اطلاعات از شما
- چه چیزی: ...
- کجا بگذارید: assets-incoming/<مسیر دقیق>
- فرمت: ...
- چرا لازم است: ...
- تا رسیدنش: ... (چه چیزی را با placeholder می‌سازم / کدام بخش منتظر می‌ماند)
```

- تا حد ممکن کار را متوقف نکن: با placeholder ادامه بده و در کد و `01-assets-needed.md` علامتش بزن.
- هرگز کلید یا محتوای ساختگی نساز که شبیه واقعی باشد.
- بعد از رسیدن فایل، وضعیت در `01-assets-needed.md` را به `✅ دریافت شد` تغییر بده.
